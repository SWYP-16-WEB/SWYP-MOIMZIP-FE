# Feature-Sliced Design 구조

이 프로젝트는 Next.js App Router 위에 FSD의 **app + views + features + entities + shared** 레이어를 적용합니다. `widgets`는 여러 기능을 조합한 큰 UI 블록이 반복될 때 팀 논의 후 추가합니다.

```text
src/
├── app/                         # Next.js 라우트, 레이아웃, 전역 프로바이더
├── views/                       # FSD pages 레이어: 화면 단위 코드
├── features/                    # 사용자 행동 단위 코드 (공유, 응답, 리마인드 설정, 로그인 등)
├── entities/                    # 도메인 데이터와 표시 UI (이벤트, 참석 응답, 사용자)
└── shared/                      # 도메인과 무관한 재사용 코드
    ├── api/                     # 공통 HTTP 클라이언트 및 API 설정
    ├── assets/                  # 정적 자원
    │   ├── svg/                 # 원본 SVG (직접 추가)
    │   ├── icons/               # SVGR 생성 아이콘 컴포넌트 (자동 생성)
    │   └── index.ts             # 아이콘 barrel (자동 생성)
    ├── config/                  # 환경·상수 설정
    ├── layout/                  # 공통 레이아웃 컴포넌트 (barrel 자동 생성)
    ├── ui/                      # 공통 UI 컴포넌트 (barrel 자동 생성)
    └── utils/                   # 공통 유틸리티
```

## `views`를 사용하는 이유

FSD의 pages 레이어는 이 프로젝트에서 `src/views`로 표기합니다. Next.js가 `src/pages`를 Pages Router의 예약 디렉터리로 인식하므로, App Router와의 충돌을 막기 위한 결정입니다.

```text
src/app   → Next.js App Router의 라우팅 레이어
src/views → FSD pages 레이어
```

## 의존성 규칙

```text
app → views → features → entities → shared
```

- 상위 레이어는 하위 레이어만 import합니다. 하위 레이어는 상위 레이어를 import하지 않습니다.
- 같은 레이어의 서로 다른 슬라이스는 직접 import하지 않습니다. (`views/home` → `views/my-events` 금지, `features/share-invitation` → `features/auth` 금지) 공통으로 필요한 코드는 하위 레이어로 옮깁니다.
- `app`과 `shared`는 슬라이스 없이 세그먼트(`api`, `ui` 등)로 나누며, 내부 참조에 슬라이스 규칙을 적용하지 않습니다.
- 슬라이스 외부에 공개할 코드는 `index.ts`로 노출하고, 다른 슬라이스는 `index.ts`를 통해서만 import합니다.
- `app/**/page.tsx`는 라우팅만 담당하며, 화면 구현은 `views`의 public API를 사용합니다.
- 레이어 방향 위반은 ESLint `no-restricted-imports`로 검사합니다. 같은 레이어의 슬라이스 간 참조는 리뷰에서 확인합니다.

## 레이어별 책임

| 레이어     | 책임                                                                    | 판단 기준                                                              |
| ---------- | ----------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| `views`    | 화면 하나의 구성과 화면 전용 컴포넌트·훅                                | 한 화면에서만 쓰이면 해당 화면 슬라이스 안에 둡니다.                   |
| `features` | 사용자가 하는 행동과 그 상태·검증·mutation                              | 두 개 이상의 화면에서 같은 행동을 하거나, 행동 로직이 화면과 분리될 때 |
| `entities` | 도메인 타입, API 요청 함수, query key, 도메인 판단 로직, 데이터 표시 UI | 여러 화면·기능이 같은 도메인 데이터를 읽거나 보여줄 때                 |
| `shared`   | 도메인을 모르는 UI·유틸·설정·통신 기반                                  | 이벤트·초대장 같은 도메인 용어가 들어가면 `shared`에 두지 않습니다.    |

슬라이스 내부는 필요한 세그먼트만 만듭니다.

```text
entities/event/
├── api/        # 요청 함수, query key, query/mutation 훅
├── model/      # 타입, 도메인 판단 로직 (상태·권한·마감 여부)
├── ui/         # 데이터 표시 컴포넌트
└── index.ts    # public API
```

## 슬라이스 배치 기준

기능명세(화면 번호 기준)와 현재 디자인 시안을 바탕으로 정한 잠정 배치입니다. 디자인과 명세가 확정되면 이 표를 갱신합니다. 빈 슬라이스 폴더는 미리 만들지 않고, 해당 화면·기능을 구현할 때 이 표를 기준으로 생성합니다.

| 레이어     | 슬라이스(예정)     | 담당                                                                                                                                         | 사용 화면                                   |
| ---------- | ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------- |
| `entities` | `event`            | 이벤트 타입·API, 진행/완료·호스트 여부·응답 마감 판단, 모임 유형별 이름·아이콘 매핑, 초대장 카드(`InvitationCard`), 목록 아이템(`EventCard`) | 1-3, 2-1, 3-1, 3-4, 4-1, 5-1, 5-2, 6-1, 7-1 |
| `entities` | `response`         | 참석 응답 타입·API, 참석/불참 집계, 참석 상태 뱃지, 집계 카드                                                                                | 2-1, 4-2                                    |
| `entities` | `user`             | 로그인 사용자 정보 조회, 회원 여부                                                                                                           | 1-1, 3-3, 4-1, 5-x                          |
| `features` | `auth`             | 카카오 로그인(버튼 포함), 로그아웃, 로그인 결과 처리                                                                                         | 1-5, 3-3, 5-3                               |
| `features` | `create-event`     | 생성 플로우 임시 데이터 (유형 → 기본 정보 → 체크리스트 → 미리보기 → 리마인드)                                                                | 3-1 ~ 3-4, 7-1, 2-3                         |
| `features` | `set-reminder`     | 리마인드 폼과 검증 (저장 방식은 상위 `views`에서 `onSubmit`으로 연결)                                                                        | 2-3 (3-4, 4-2에서 진입)                     |
| `features` | `share-invitation` | 공유 URL 복사, 카카오톡 공유                                                                                                                 | 4-1, 6-1                                    |

- 진행 중인 이벤트 상세(1-4)와 초대장 수정(6-1)은 디자인 시안에서 하나의 화면으로 통합되었습니다. 접속자 권한(주최자/참여자)에 따라 하단 버튼을 분기하는 `views` 슬라이스 하나로 구현합니다. 완료된 이벤트(1-3)는 별도 슬라이스로 둡니다.
- 기본 정보 폼(3-2)은 생성·수정 경로가 같은 `views` 슬라이스에 `mode`를 다르게 넘겨 재사용합니다.
- 한 화면에서만 쓰이는 UI는 `views` 슬라이스 내부에 둡니다. (유형 타일(3-1), 준비 옵션 카드(3-3), 체크리스트 항목·원형 진행률·항목 바텀시트(7-1 ~ 7-3))
- 참석/불참 응답 제출(기기별 응답 기록, 중복 제출 방지 포함)은 2-1에서만 쓰이므로 `views` 슬라이스 내부에 둡니다. 다른 화면에서 응답 기능이 필요해지면 `features`로 옮깁니다.
- 회원 화면(5-1, 5-2)의 하단 탭바는 회원 전용 route group의 `layout.tsx`에서 배치합니다.

### 리마인드 저장 방식 연결 (feature 간 의존 방지)

리마인드 폼(`features/set-reminder`)은 진입 경로에 따라 저장 방식이 다릅니다. 생성 중(3-4에서 진입)에는 이벤트가 아직 DB에 없어 `features/create-event`의 임시 데이터를 갱신하고, 생성 후(4-2에서 진입)에는 API로 바로 저장합니다.

이때 `set-reminder`가 `create-event`를 직접 import하면 같은 레이어의 슬라이스 간 참조가 되어 의존성 규칙을 위반합니다. 그래서 `set-reminder`는 폼 UI·검증만 담당하고 저장 동작은 `onSubmit`으로 받으며, 두 feature를 함께 import할 수 있는 상위 `views`에서 `onSubmit`을 연결합니다.

| 진입 경로     | `onSubmit`에 연결하는 동작                      | 연결 위치 |
| ------------- | ----------------------------------------------- | --------- |
| 생성 중 (3-4) | `features/create-event`의 임시 데이터 갱신      | `views`   |
| 생성 후 (4-2) | `entities/event`(또는 리마인드 API)의 저장 요청 | `views`   |

```tsx
// views 슬라이스에서 두 feature를 조합 (예시, 실제 이름은 구현 시 확정)
import { useCreateEventDraft } from '@/features/create-event';
import { ReminderForm } from '@/features/set-reminder';

const { setReminder } = useCreateEventDraft();

<ReminderForm onSubmit={setReminder} />;
```

- `features/set-reminder` 내부에서 `@/features/create-event`를 import하지 않습니다.
- 같은 방식으로, 여러 feature를 함께 써야 하는 동작은 feature끼리 참조하지 않고 상위 `views`에서 조합합니다.

### `shared/ui` 후보

디자인 시안에서 여러 화면에 반복되고 도메인 용어가 없는 UI입니다. 실제로 사용하는 화면을 구현할 때 함께 추가합니다.

| 분류     | 컴포넌트                                                                                        |
| -------- | ----------------------------------------------------------------------------------------------- |
| 버튼     | 하단 CTA 버튼(Large), Small 버튼, 칩 버튼, 텍스트 링크 버튼                                     |
| 입력     | 라인 입력(라벨·필수 표시·에러 문구·글자 수 카운터), 라벨+값 정보 필드, 복사 버튼이 있는 값 필드 |
| 선택     | 캘린더, 시간·분 선택, 세그먼트 컨트롤(필터 칩), 이미지 업로드                                   |
| 오버레이 | 바텀시트, 토스트(시안 미정)                                                                     |
| 레이아웃 | 헤더(뒤로가기·로고·사용자 아이콘 슬롯), 하단 탭바, 봉투 틀(`Envelope`)                          |

- 봉투 틀은 상단 아이콘과 내부 콘텐츠를 slot으로 받는 장식 컴포넌트로 `shared/ui`에 두고, 그 안에 들어가는 초대장 내용은 `entities/event`의 `InvitationCard`가 담당합니다. 기본 정보 폼(3-2)처럼 초대장 대신 폼이 들어가는 화면도 같은 틀을 사용합니다.

## 인증 (미확정)

인증 방식은 아직 확정되지 않았습니다. JWT를 검토 중이며, 아래 항목이 서버와 합의되면 인증 코드를 구현하고 이 섹션을 갱신합니다. 확정 전에는 토큰 저장·헤더 부착 코드를 미리 추가하지 않습니다.

| 결정 필요 항목                                     | 영향                                                                                                         |
| -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| access token 전달 방식 (응답 본문 / httpOnly 쿠키) | 응답 본문이면 프론트가 토큰을 보관하고 `Authorization` 헤더를 부착, 쿠키면 `withCredentials`만 설정          |
| refresh token 보관 위치와 재발급 API, 만료 시간    | 401 응답 시 재발급 후 재요청하는 interceptor 구현 방식                                                       |
| 카카오 로그인 콜백 처리 주체 (프론트 / 백엔드)     | 콜백 route(`app/`) 필요 여부, 토큰을 받는 시점                                                               |
| 인증 쿠키의 도메인                                 | 쿠키가 API 서버 도메인에만 있으면 Next.js `proxy.ts`에서 읽을 수 없어 회원 전용 화면 접근 제어 방식이 달라짐 |

확정 후 코드는 아래 위치에 배치합니다.

| 위치                   | 책임                                                        |
| ---------------------- | ----------------------------------------------------------- |
| `shared/api`           | 공통 HTTP 클라이언트의 인증 헤더·쿠키 설정, 401 재발급 처리 |
| `features/auth` (예정) | 카카오 로그인, 로그아웃, 로그인 결과 처리                   |
| `entities/user` (예정) | 현재 사용자 조회, 회원 여부 판단                            |

## 레이어 추가 기준

아래와 같은 필요가 생기면 **팀 논의 후** 해당 레이어를 추가하고, 이 문서의 구조와 의존성 규칙, ESLint 설정을 함께 갱신합니다.

| 레이어    | 추가 시점                                                                                          |
| --------- | -------------------------------------------------------------------------------------------------- |
| `widgets` | 여러 기능과 도메인을 조합한 큰 UI 블록(예: 초대장 카드 + 공유 버튼 묶음)이 여러 화면에서 반복될 때 |

레이어를 모두 추가하면 의존 방향은 `app → views → widgets → features → entities → shared`가 됩니다.
