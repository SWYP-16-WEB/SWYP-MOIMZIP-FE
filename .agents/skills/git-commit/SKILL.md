# 커밋

변경사항을 `commit.md` 기준으로 나눠 커밋합니다. 커밋은 사용자가 요청한 범위에서만 하고, push는 별도 요청이 있을 때만 합니다.

## 참조 문서

아래 링크는 이 스킬 파일 기준 상대 경로입니다. 명령은 저장소 루트에서 실행합니다.

- [커밋 메시지·분리 기준·절차](../../../docs/conventions/commit.md)
- [브랜치 규칙](../../../docs/conventions/git-convention.md)
- [Git hook(lint-staged) 동작](../../../docs/conventions/tooling.md)

## 트리거

- 사용자가 커밋을 요청할 때
- 커밋을 어떻게 나눌지, 메시지를 어떻게 쓸지 물을 때

## 해야 할 일

1. 브랜치를 확인합니다. `develop`·`main`에 직접 커밋하지 않습니다. 해당 브랜치에 있으면 `git-convention.md` 이름 규칙에 맞는 작업 브랜치가 필요하다고 알리고, 이슈 번호를 확인합니다.
2. `git status`, `git diff`, `git diff --cached`로 전체 변경을 확인합니다. 이번 요청과 관계없어 보이는 변경(사용자가 다른 작업 중인 파일 등)이 있으면 포함할지 묻습니다. 사용자 변경을 되돌리거나 임의로 커밋에 섞지 않습니다.
3. `commit.md`의 분리 기준으로 변경을 그룹으로 나눕니다. 이 저장소에서 자주 나오는 분리 예시입니다.
   - 생성 스크립트 수정과 그 결과로 다시 만든 생성 파일(아이콘 등)은 원인이 다르므로 나눕니다.
   - 리뷰 반영 수정은 리뷰 내용 단위로 커밋합니다.
   - 구조 규칙 변경과 그에 따른 문서·설정 갱신은 같은 이유면 함께, 여러 변경에 걸친 문서 정리면 `docs`로 따로 둡니다.
4. 커밋 계획(그룹별 파일과 메시지)을 먼저 보여줍니다. 사용자가 바로 커밋을 요청했고 나누는 기준이 분명하면 계획을 공유하면서 진행합니다.
5. 그룹마다 필요한 파일만 `git add <파일>`로 올리고 `git diff --cached`로 확인한 뒤 커밋합니다. `git add -A`나 `git add .`로 한 번에 올리지 않습니다. `.env` 등 비밀값 파일이 올라가지 않았는지 확인합니다.
6. 커밋 시 pre-commit 훅(lint-staged)이 파일을 고치거나 오류로 중단할 수 있습니다. 오류를 고친 뒤 다시 커밋하고, `--no-verify`로 훅을 건너뛰지 않습니다. 이미 만든 커밋을 `--amend`로 바꾸는 것은 사용자가 요청할 때만 합니다.
7. 커밋 메시지 끝에 붙이는 서명(trailer) 등 추가 규칙은 사용자·실행 환경의 지시를 따릅니다.

## 결과 보고

- 만든 커밋 목록: 해시, 메시지, 포함 파일
- 커밋하지 않고 남긴 변경과 그 이유
- push하지 않았다는 점 (요청이 없었다면)

## 점검해야 할 내용

- 커밋마다 하나의 목적만 담겼고 접두사가 변경 성격과 맞는지 확인합니다.
- 제목이 한 줄이고 끝에 마침표가 없는지 확인합니다. 이유가 필요한 변경에는 본문을 썼는지 확인합니다.
- 커밋 후 `git status`로 의도하지 않은 파일이 남거나 빠지지 않았는지 확인합니다.
