# 프로젝트 규칙 확인

구현을 시작하기 전에 작업 범위, 브랜치 상태, 코드 배치, 미확정 사항을 정리합니다. 이 스킬은 판단 순서만 안내하며, 규칙의 원문은 아래 문서에 있습니다. 문서와 이 스킬이 다르면 문서를 따르고 차이를 사용자에게 알립니다.

## 참조 문서

아래 링크는 이 스킬 파일 기준 상대 경로입니다. 명령은 저장소 루트에서 실행합니다.

- [작업·검증 절차, 스킬 라우팅](../../../AGENTS.md)
- [레이어 구조·의존성·슬라이스 배치 기준](../../../docs/architecture/fsd.md)
- [코딩·스타일링 컨벤션](../../../docs/conventions/dev-convention.md)
- [포맷팅·Lint·생성 스크립트](../../../docs/conventions/tooling.md)
- [브랜치·PR 규칙](../../../docs/conventions/git-convention.md), [커밋 규칙](../../../docs/conventions/commit.md)
- Next.js API는 학습 데이터와 다를 수 있으므로 `node_modules/next/dist/docs/`의 해당 가이드를 확인합니다.

## 트리거

- 새 화면·기능·컴포넌트·API 연동 구현을 시작할 때
- 코드를 어느 레이어·슬라이스에 둘지 정하거나, 기존 배치가 맞는지 검토할 때
- 레이어·의존성·폴더 규칙을 추가하거나 바꿀 때
- 기획 문서(PRD, 기능명세, 디자인 시안)를 바탕으로 구현 범위를 정할 때

## 해야 할 일

### 1. 작업 상태와 범위 확인

- `git branch --show-current`, `git status`, `git diff`, `git diff --cached`로 현재 상태를 확인합니다.
- 요청이 현재 브랜치의 작업 범위(브랜치 이름의 이슈·작업 내용)와 다르면 구현 전에 사용자에게 알리고 어디서 작업할지 확인합니다. 범위가 섞이면 PR 리뷰와 되돌리기가 어려워집니다.
- 커밋되지 않은 사용자 변경과 작업 중 바뀐 파일은 사용자 의도로 보고 되돌리지 않습니다. 생성 파일을 정리할 때도 `git checkout`으로 덮어쓰기 전에 커밋 여부를 확인합니다.
- `AGENTS.md`의 Skill Routing에서 해당 작업 스킬을 찾고, 사용 가능한 `SKILL.md`가 있으면 이어서 읽습니다.

### 2. 코드 배치 판단

`fsd.md`의 레이어별 책임과 슬라이스 배치 표를 먼저 확인합니다. 표에 있는 슬라이스는 그 이름과 담당 범위를 따릅니다. 표에 없으면 사용 화면 수보다 **코드의 역할과 바뀌는 이유**를 먼저 보고 판단합니다. 사용 화면 수는 역할이 애매할 때 참고하는 보조 기준입니다.

| 코드의 역할                                                   | 배치                                                                                                                                                                                               |
| ------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 라우팅·레이아웃·전역 프로바이더                               | `app` (`page.tsx`는 `views`의 public API만 연결)                                                                                                                                                   |
| 화면 구성, 그 화면의 배치·문구에 묶인 UI                      | `views` 슬라이스 안. 화면이 바뀔 때 함께 바뀌는 코드입니다.                                                                                                                                        |
| 사용자 행동(제출·공유·로그인 등)과 그 상태·검증·요청          | 화면 구성과 다른 이유로 바뀌면 `features` (예: 외부 SDK 연동, 별도 정책을 따르는 검증). 여러 화면에서 같은 행동을 하면 분리 근거가 더 분명합니다. 화면과 함께 바뀌는 단순 처리면 `views`에 둡니다. |
| 여러 화면·기능이 읽거나 보여주는 도메인 데이터                | `entities` (타입, API 요청 함수, query key, 도메인 판단 로직, 표시 전용 UI)                                                                                                                        |
| 도메인 용어(이벤트, 초대장, 응답 등)가 없는 기반 UI·유틸·설정 | `shared`. 처음 쓰는 화면이 하나뿐이어도 역할이 범용이면 `shared`입니다. 도메인 용어가 들어가면 `shared`에 두지 않습니다.                                                                           |

새 사용자 행동이라는 이유만으로 `features`를 만들지 않습니다. 분리한다면 화면과 별개로 바뀌는 근거를 결과에 함께 적습니다.

판단할 때 함께 지킬 원칙입니다.

- 몇 번 쓰이는지보다 왜 바뀌는지로 나눕니다. 모양이 비슷해도 변경 이유가 다르면 합치지 않습니다.
- 같은 레이어의 슬라이스끼리 import하지 않습니다. 한 feature가 다른 feature의 동작을 필요로 하면 두 feature를 import할 수 있는 상위 `views`에서 조합하고, 필요한 동작은 `onSubmit` 같은 props로 주입합니다.
- 슬라이스 외부 공개는 `index.ts`로 하고, 다른 슬라이스는 `index.ts`만 import합니다.
- 빈 슬라이스 폴더를 미리 만들지 않습니다. 실제 코드와 함께 만들고, 표에 없는 슬라이스를 새로 만들면 `fsd.md` 배치 표에 추가합니다.
- `widgets` 등 새 레이어는 팀 합의 없이 추가하지 않습니다. 필요해 보이면 근거와 함께 제안합니다.

### 3. 미확정 사항과 기획 차이 처리

- API 명세, 인증 방식, URL 설계, 디자인처럼 확정되지 않은 정책은 코드로 미리 정하지 않습니다. 한쪽 방식을 전제로 한 코드는 확정 후 통째로 바뀌거나 쓰이지 않는 코드가 됩니다. 대신 결정이 필요한 항목과 영향 범위를 사용자에게 알리고, 구조 문서에 남길 내용이면 `fsd.md`에 "미확정" 항목으로 정리합니다.
- PRD, 기능명세, 웹플로우, 디자인 시안이 서로 다르면 임의로 하나를 고르지 않고 차이를 표로 정리해 확인을 요청합니다. 디자인 시안이 다른 문서의 미결 사항을 정리해 주는 경우에도 그 판단을 근거와 함께 보고합니다.
- 접근할 수 없는 자료(권한 없는 노션 페이지 등)는 추측으로 채우지 않고 접근할 수 없다고 알립니다.

### 4. 규칙을 바꿀 때 함께 고칠 곳

레이어·의존성·폴더 규칙은 여러 파일에 반영되어 있습니다. 하나만 바꾸면 에이전트, 리뷰 봇, Lint의 기준이 서로 달라집니다. 규칙을 바꾸면 아래를 모두 확인합니다.

| 파일                                               | 반영 내용                                  |
| -------------------------------------------------- | ------------------------------------------ |
| `docs/architecture/fsd.md`                         | 구조, 의존성 규칙, 슬라이스 배치 표        |
| `eslint.config.mjs`                                | 레이어 순서 배열과 `no-restricted-imports` |
| `docs/conventions/tooling.md`                      | ESLint 규칙 설명                           |
| `.coderabbit.yaml`                                 | 경로별 리뷰 기준                           |
| `AGENTS.md`                                        | 기본 규칙의 구조 설명                      |
| `.agents/agents/*.md`, `.agents/skills/*/SKILL.md` | 역할·스킬 지침의 구조 설명                 |

ESLint 레이어 규칙을 바꾸면 위반 import를 가진 임시 파일로 실제 에러가 나는지 확인한 뒤 임시 파일을 지웁니다.

### 5. 작업 시작 전 정리

구현 전에 사용자에게 아래 내용을 짧게 공유합니다. 판단이 분명한 항목은 공유만 하고, 사용자 결정이 필요한 항목만 묻습니다.

- 현재 브랜치와 작업 범위 일치 여부
- 만들거나 고칠 파일과 배치 레이어·슬라이스, 그렇게 둔 이유
- 미확정이라 이번 작업에서 정하지 않을 항목
- 실행할 검증 (`AGENTS.md` 검증 절차 기준)

## 점검해야 할 내용

- 배치한 코드가 상위 레이어나 같은 레이어의 다른 슬라이스를 import하지 않는지 확인합니다.
- 배치가 코드의 역할과 맞는지 확인합니다. 화면에 묶인 UI를 하위 레이어로 내리거나, 도메인 코드를 `shared`에 두거나, 분리 근거 없이 `features`를 만들지 않았는지 봅니다.
- 미확정 정책을 전제로 한 코드나 쓰이지 않는 코드를 추가하지 않았는지 확인합니다.
- 규칙을 바꿨다면 4번 표의 파일이 모두 같은 기준을 말하는지 확인합니다.
- 컨벤션 원문(`dev-convention.md`)과 다르게 IDE 제안을 그대로 적용하지 않았는지 확인합니다. (예: rem 임의값을 Tailwind 기본 스케일로 바꾸라는 제안)
- 실행하지 못한 검증, 접근하지 못한 자료, 문서 간 불일치는 결과에 명시합니다.
