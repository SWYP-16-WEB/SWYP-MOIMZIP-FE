# 코드 품질 점검

이번 작업에서 바뀐 코드가 프로젝트 기준을 지키는지 확인하고, 범위 안의 문제를 고친 뒤 결과를 보고합니다. 기준의 원문은 아래 문서에 있으며 이 스킬에 복사하지 않습니다.

## 트리거

- 구현을 마무리할 때, 커밋·PR 전에 변경을 확인할 때
- 리팩터링, Lint·빌드 오류 수정을 요청받았을 때
- 사용자가 코드 점검·정리를 요청할 때

## 해야 할 일

1. 점검 범위를 정합니다. `git status`, `git diff`, `git diff --cached`로 이번 작업의 변경을 확인하고, 새 파일은 내용을 직접 읽습니다. 범위 밖의 기존 코드 문제는 고치지 않고 보고만 합니다. 범위를 넘는 수정은 리뷰와 되돌리기를 어렵게 합니다.
2. 자동 검증을 `AGENTS.md` 순서대로 실행합니다: `pnpm format:check` → `pnpm lint` → `pnpm build`. 문서만 바뀌었으면 해당 문서에 `pnpm exec prettier --check`를 실행합니다.
3. 자동 수정이 필요하면 변경 파일에만 `eslint --fix`, `prettier --write`를 적용하고 검증을 다시 실행합니다. 오류를 없애려고 규칙을 끄거나 `eslint-disable`을 추가하지 않습니다.
4. 자동 검증이 잡지 못하는 항목을 확인합니다.
   - 컨벤션: 이름, export 방식, 조건문·반복문, 비동기 처리, 주석 위치 (`dev-convention.md`)
   - 스타일: 수치는 rem 임의값, 컬러·타이포그래피는 토큰 사용. IDE가 제안하는 Tailwind 기본 스케일 클래스로 바꾸지 않습니다.
   - 레이어: 같은 레이어의 다른 슬라이스 import, 한 화면 전용 코드를 하위 레이어로 내린 경우, 도메인 코드를 `shared`에 둔 경우 (ESLint는 레이어 방향만 검사합니다)
   - 남은 코드: 미사용 코드·import, `console.log` 등 디버그 출력, 임시 코드, 주석 처리된 코드, 충돌 마커
   - 미확정 정책을 전제로 한 코드나 아직 쓰이지 않는 코드
   - 서버 연동: 로딩·에러·빈 상태, 중복 제출 방지
   - 접근성: 의미에 맞는 태그, 아이콘 버튼의 접근 가능한 이름, 폼 라벨, 비활성 상태
   - 보안: 실제 환경변수 값·비밀키, 클라이언트에 노출되는 서버 전용 값
   - 생성 파일: 아이콘·barrel 등 자동 생성 파일을 직접 수정하지 않고 스크립트(`pnpm build:icons`, `pnpm barrels`)로 다시 만들었는지
5. 범위 안의 문제를 고치고 2번 검증을 다시 실행합니다. 판단이 필요한 수정(동작이 바뀌는 리팩터링, 정책 결정)은 고치기 전에 사용자에게 확인합니다.

## 결과 보고

아래 순서로 짧게 보고합니다.

- 고친 문제: 파일·라인, 무엇을 왜 고쳤는지
- 남은 문제: 중요도순, 파일·라인, 영향, 고치지 않은 이유(범위 밖, 결정 필요 등)
- 검증 결과: 실행한 명령과 통과·실패 여부. 실행하지 못한 검증은 이유와 함께 적고 통과로 보고하지 않습니다.

## 점검해야 할 내용

- 범위 밖의 코드를 고치거나 사용자 변경을 되돌리지 않았는지 확인합니다.
- 규칙을 끄거나 우회해서 검증을 통과시키지 않았는지 확인합니다.
- 최종 `git diff`에 충돌 마커, 중복·미사용 import, 임시 코드, 디버그 출력이 없는지 확인합니다.
- 리뷰만 요청받은 경우(`fe-reviewer` 역할 등)에는 파일을 수정하지 않고 결과만 보고합니다.
