# PR 작성

현재 브랜치의 실제 변경을 바탕으로 PR 제목과 본문을 작성합니다. 기본 출력은 사용자가 복사해 붙여 넣을 수 있는 채팅 텍스트이며, 파일을 만들거나 PR을 직접 생성하는 것은 요청이 있을 때만 합니다.

## 참조 문서

아래 링크는 이 스킬 파일 기준 상대 경로입니다. 명령은 저장소 루트에서 실행합니다.

- [PR 제목 규칙·항목별 작성 요령·대상 브랜치](../../../docs/conventions/git-convention.md)
- [PR 본문 템플릿](../../../.github/pull_request_template.md)
- [커밋 접두사](../../../docs/conventions/commit.md)

## 트리거

- PR 제목·본문 작성을 요청받을 때
- 리뷰 반영, 추가 커밋, 범위 변경으로 기존 PR 본문을 고쳐야 할 때

## 해야 할 일

1. 변경 범위를 확인합니다. PR 대상은 `develop`입니다.
   - 로컬 `develop`은 없거나 오래되었을 수 있습니다. 그러면 이미 대상 브랜치에 들어간 커밋까지 PR 변경으로 보입니다. 먼저 `git fetch origin develop`으로 최신 원격 브랜치를 가져오고, 원격 ref를 기준으로 비교합니다.
   - `git log origin/develop..HEAD --oneline`, `git diff origin/develop...HEAD --stat`으로 PR에 들어갈 커밋과 파일을 확인하고, 필요한 파일은 diff를 읽습니다.
   - 사용자가 다른 대상 브랜치를 지정하면 같은 방식으로 그 원격 ref(`origin/<대상>`)를 기준으로 비교합니다.
   - 커밋되지 않은 변경이 있으면 PR에 포함되지 않는다고 알리고, 본문에 넣을지 묻습니다. 본문과 실제 PR 내용이 어긋나지 않게 합니다.
   - 연관 이슈 번호는 브랜치 이름(`{접두사}/#{이슈}/{작업}`)에서 가져옵니다.
2. 제목은 `[접두사] 작업 내용` 형식으로, 접두사는 커밋 접두사의 첫 글자만 대문자로 씁니다.
3. 템플릿의 항목과 순서를 그대로 사용해 본문을 씁니다.
   - **🔗 연관된 이슈**: `closes #이슈번호`
   - **📝 작업 내용**: 작업을 번호로 나열하고, 각 작업마다 무엇을 바꿨는지와 왜 그 방식을 택했는지 씁니다. 바꾼 파일, 값, 판단 근거가 많으면 표로 정리합니다. 일부러 하지 않은 것과 그 이유도 적습니다. 리뷰어가 같은 질문을 하지 않게 하기 위해서입니다.
   - **💬 공유 사항**: 리뷰어가 특히 봐 줬으면 하는 판단, 미확정이라 이번 PR에서 정하지 않은 것과 영향 범위, 기획 문서 간 차이처럼 논의가 필요한 내용을 씁니다.
   - **📸 스크린샷**: UI 변경이 있으면 첨부할 화면(예: 모바일 폭 화면)을 안내합니다. 없으면 "UI 변경 없음"으로 씁니다.
   - **ETC**: 실행한 검증과 결과(통과·실패·미실행), 후속 작업을 씁니다.
4. 본문은 실제로 실행한 검증만 통과로 적습니다. 실행하지 못한 검증과 확인하지 못한 환경은 그대로 밝힙니다.
5. Figma 등 프로젝트 외부 자료의 링크는 본문에 넣지 않고 이름으로만 언급합니다.
6. 출력할 때 제목과 본문을 각각 코드 블록에 담아 그대로 복사할 수 있게 합니다. 본문 안에 코드 블록이 있으면 바깥 블록은 백틱 4개(````)로 감쌉니다.
7. PR 마지막 서명 등 추가 규칙은 사용자·실행 환경의 지시를 따릅니다.

## 리뷰·변경 반영

- 리뷰를 반영해 코드·문서를 고쳤다면, 바뀐 항목만 교체할 수 있게 "어느 항목을 무엇으로 바꿀지"를 먼저 제공합니다. 사용자가 합본을 원하면 전체 본문을 다시 출력합니다.
- 리뷰 코멘트에 남길 답글 초안을 함께 제공합니다. 무엇을 어디에 반영했는지 한두 문장으로 씁니다.
- 본문을 쓴 뒤 코드·문서가 바뀌면 본문과 실제 내용이 맞는지 다시 확인하고, 어긋나는 부분을 알려 줍니다.

## 점검해야 할 내용

- 본문에 적은 변경이 모두 실제 PR 범위(커밋된 변경)에 있는지 확인합니다.
- 작업 내용마다 "왜"가 들어 있고, 팀원이 대화 맥락 없이 읽어도 이해되는지 확인합니다.
- 템플릿 항목을 빼거나 순서를 바꾸지 않았는지 확인합니다.
- PR 생성(`gh pr create`)이나 push는 사용자가 요청했을 때만 하고, 실행 전에 대상 브랜치와 제목을 확인합니다.
